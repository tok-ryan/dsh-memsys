# 记忆系统小评测

> 起因：B站 上有人吐槽"记忆插件能不能过 BM25 都是两码事，都是纯许愿"。
> 这份评测就是回答那句话的——**先量一下我们自己的底**，不管好看难看。

## 一、协议

| 项 | 内容 |
|---|---|
| 数据 | `memsys-whalesoul-data`（25 条真实记忆） |
| 题目 | 20 道口语化题目，Codex 根据记忆库自动生成（覆盖 25 条记忆 + 3 道陷阱题） |
| 模型 | 与主会话同档（flash），每题**独立上下文**，60 次隔离作答 |
| 判分 | 每题预置 2~3 个 must-have 事实点；二元组召回 + 连续片段双档匹配，人工抽检 |

**三配置**

| 配置 | 上下文 |
|---|---|
| **A 裸模型** | 空 |
| **B 纯 BM25** | 关键词检索 top-3，只给记忆原文 |
| **C memsys** | 同一检索算法，top-5 + 类型/权重/日期/why 元数据 |

> 诚实说明：C 没有换检索算法（memsys 检索层本质也是关键词），差别只在**条数 + 元数据 + why 字段**。
> 所以这套评测量的是"多一点上下文和元数据有没有用"，**不是**"memsys 检索强于 BM25"。

## 二、结果

### 检索召回（金标准记忆有没有被捞到）

| | 金标准条目 | 命中 | 召回率 |
|---|---|---|---|
| B 纯 BM25 | 26 | 13 | **50%** |
| C memsys | 26 | 17 | **65%** |

### 回答覆盖（must-have 事实点命中）

| | 命中 | 总数 | 覆盖率 |
|---|---|---|---|
| **A 裸模型** | 5 | 52 | **9.6%** |
| **B 纯 BM25** | 25 | 52 | **48.1%** |
| **C memsys** | 28 | 52 | **53.8%** |

逐题明细见 `eval/scores20.json`。

### 三个典型失败

- **c08「我那几条创作线做到哪儿了」**：记忆里明明有《钢铁黎明》26 章、《AI狂飙》、civ-evo 进度，B/C **一条都没捞到**，只能答"记忆里没有"。
- **c17「给我对象做的小网页叫啥」**：`生活指南针 v1.0.0` 在库里，B/C 同样零召回。
- **c04「小苏这个称呼对我有啥好处」**：正确答法是"补木、丙火身弱喜木"，B/C 只答到一半（B 甚至没捞到记忆，靠猜）。

### 陷阱题（3 道，正解是"不确定"）

c18 女友生日具体日期 / c19 智齿后来拔没拔 / c20 月到手工资 —— **A/B/C 全部答对**。
说明这类"库里确实没有"的题，三档都靠"不知道"过关，**区分度为零**，下次要换成"库里有一条相似的干扰项"才有意义。

## 三、结论（照实说）

1. **有记忆 >> 没记忆**：9.6% → 48%，五倍。
2. **C 比 B 高 5.7 个百分点**，但这点差距在 20 题样本下**不构成显著优势**——多捞的两条记忆大多不是判分点。
3. **瓶颈在检索，不在模型**：C 的召回只有 65%，凡是没召回的记忆，模型一律答"不确定"——这不是模型不行，是**没喂到**。
4. **所以那条评论说得对**：至少在我们这套实现上，"关键词检索 + 记忆注入"不能保证答对，**口语化提问会直接掉链子**（c08/c17 就是活证据）。

## 四、局限（别拿这份报告吹牛）

- 20 题由 Codex 从记忆反向生成，**偏 synthetic**：题目围绕"库里有的东西"出，不能代表真实使用分布。
- 判分是我写的 must-have + 规则匹配，同义表述会漏判（已用双档匹配缓解，仍不完美）。
- C 与 B 检索算法相同，**没有验证"语义检索能不能救 c08/c17"**。
- 单一模型、单次采样，没有多次取平均。

## 五、下一步（0.3.1 方向）

1. **查询改写**：问句先抽检索词（"挥霍 token" → 成本/花费/测算/浪费）。
2. **把 `why` 纳入检索**：现在 `why` 只用来出题，不参与检索。
3. **同义/口语映射表**：贴吧/日常口语词 → 记忆里的写法（"创作线" → 钢铁黎明/AI狂飙/civ-evo）。
4. 评测扩到 60~100 题，并加一组"真实会话提问"（从历史对话里挖）做对照。

## 六、复现

```bash
node eval/build-prompts.mjs          # 生成 60 份隔离问答任务（A/B/C × 20 题）
# 用任意模型逐个作答后，按 questions-codex.json 里的 must 判分
```

- 题目：`eval/questions-codex.json`（Codex 生成，含 gold_memory_ids 与 must）
- 记忆导出：`eval/memories-export.md`
- 回答与得分：`eval/answers20-{a,b,c}.json`、`eval/scores20.json`

**口径变了，两张表不可直接横比：**

1. C 配置从「BM25 top5 + 元数据」改成「**memsys 检索层 top5**（`searchMemories(keywords=原问句)`）+ 元数据」——
   0.3.0 的 C 其实没走 memsys 检索层，这次才是真测它。
2. 判分器入库（`eval/grade.mjs`，规则 `eval/must-match.mjs`）：must 点命中 = **变体连续片段 ≥4 字**

   **同一个脚本重判一份**并列（旧 A/B/C 重判 5/23/26，人工 5/25/28，差 4 个 must 点是同义改写被严格脚本误杀）。

### 新增局限

- 20 题仍是从这 25 条记忆反向生成的 synthetic 题，**扩展词表针对性很强，别当通用检索能力**；
  去掉本地私人别名（`aliases.json`）后召回会回到 24/26（少的两条是 c08 的创作线实体），
  说明「口语→实体名」这条命是用户自己的数据给的。
- 判分脚本比人工严：同义改写、数字口径不同都会被误杀，所以 75.0% 应读作下限。
- 仍是单次采样、单一模型，没有多次取平均。
